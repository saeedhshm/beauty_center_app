# الدفع والتأكيد والاسترجاع — المرحلة 6

## القرارات المعتمدة والتنفيذ

- مزود **Demo** قابل للاستبدال (`provider: demo`)؛ لا تتحرك أموال حقيقية. القرارات
  المالية غير المحسومة (نطاق الاسترجاع، النجاح المتأخر) طُبقت كـdefaults مقترحة
  موثقة أدناه، بانتظار اعتماد المنتج.
- بدء الدفع `POST /bookings/:id/payments` للعميلة صاحبة الحجز المؤهل (`accepted`
  غير منتهي المهلة) فقط. المهلة المنتهية تُحفظ مع سجلها وإشعارها أولًا ثم يرد 409.
  المبلغ والعملة من لقطة الحجز على الخادم دائمًا.
  طلب ثانٍ يعيد أحدث `pending` مع تدوير التوكن (200) بدل تكديس النوايا.
  الدفع المسجل (`paid/refunded`) يرد `409 PAYMENT_ALREADY_SETTLED`.
- الـWebhook `POST /webhooks/payments/demo` بلا جلسة مستخدم؛ تحققه التوكن المعتم
  الخاص بكل نية (يُكشف مرة واحدة عند البدء ويُخزن HMAC/SHA-256 فقط).
  مزود حقيقي سيتحقق من التوقيع بدل التوكن — العقد (`eventId`, `outcome`, `amount`,
  `currency`) مصمم للانتقال دون تغيير شكل الحدث.
- منع التكرار دائم في `payment_provider_events` بمفتاح `(provider, event_id)` الفريد؛
  التكرار المتزامن يفوز فيه إدخال واحد والبقية no-op برمز 200. إعادة التشغيل بعد
  `paid/refunded` لا تكرر الأثر ولا سجل الحالة. حقل `confirmed` يعكس صف الحجز دائمًا،
  فتكرار حدث متأخر يرد `confirmed: false` والحجز منتهٍ.
- مبلغ الحدث وعملته يُطابقان السجل (`AMOUNT_MISMATCH` → 409، وتُعلّم المحاولة
  `failed` إن كانت `pending`). نجاح شاشة التطبيق أو إعادة التوجيه ليس دليل تحصيل؛
  التأكيد يحدث فقط داخل معاملة Webhook الموثوقة (الدفع + `accepted→confirmed` +
  السجل معًا، والفاعل نظام `changed_by NULL`).
- النجاح المتأخر (بعد انتهاء المهلة أو الإلغاء/الرفض): يُسجل الدفع `paid` كواقعة
  مالية دون تأكيد الحجز (`confirmed: false` مع `note`)، ولا يُعاد تأكيد موعد مشغول.
  التسوية اللاحقة (استرجاع تشغيلي) مسؤولية الإدارة عبر API الاسترجاع.
- الاسترجاع `POST /admin/payments/:id/refund` للإدارة فقط، وكامل المبلغ فقط
  (`refundedAmount = amount`؛ الجزئي غير معتمد رغم وجود العمود).
  حجز `confirmed` المرتبط يُلغى في المعاملة نفسها (الفاعل: المدير، والسبب محفوظ)؛
  حجز `completed` مرفوض بـ409 حتى تُعتمد سياسة ما بعد التنفيذ، والحجز المربوط
  بتحويل مسجل مرفوض بـ409 `BOOKING_IN_PAYOUT` حتى يُعالج التحويل تشغيليًا
  (راجع `payouts.md`). الاسترجاع الناجح ينشئ إشعار `payment_refunded` للعميلة
  والخبيرة في المعاملة نفسها، وإعادة الطلب لا تكرره. هذا النطاق مقترح مؤقت
  بانتظار اعتماد المنتج.

## APIs المنفذة (تحت `/api/v1`)

- `POST /bookings/:id/payments` (عميلة) — بدء/إعادة نية demo.
- `GET /bookings/:id/payments` (طرف الحجز) — محاولات الحجز.
- `POST /webhooks/payments/demo` (عام بتوكن الحدث) — حدث `paid`/`failed` مع
  `paymentId, eventId, outcome, amount, currency, token`.
- `GET /admin/payments` (فلترة `status, bookingId`) و`POST /admin/payments/:id/refund`.
- الأخطاء: `INVALID_PROVIDER_TOKEN` (401)، `PAYMENT_ALREADY_SETTLED` و`AMOUNT_MISMATCH`
  (409)، مع `BOOKING_EXPIRED` و`INVALID_TRANSITION` و404 لغير الطرف.

  التكرار no-op بسجل تأكيد واحد (`confirmed` من صف الحجز)، التوكن الخاطئ والمبلغ المختلف
  والفشل دون تأكيد، النجاح المتأخر تحت سباق قبول/انتهاء مع بقاء الانتهاء محفوظًا،
  والاسترجاع الإداري مع إلغاء ذري وإشعار الطرفين وإعادة تشغيل idempotent ورفض
  استرجاع `pending`.
