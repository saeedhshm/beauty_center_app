# الحسابات — الهاتف وكلمة المرور وOTP التسجيل

## القرار والنطاق

اعتمد المستخدم الدخول للعميلة والخبيرة برقم الهاتف وكلمة مرور، واستخدام OTP عند التسجيل للتحقق من الهاتف. التنفيذ يجعل تحقق OTP إلزاميًا قبل إنشاء الحساب لأول مرة. لا يطلب OTP عند كل دخول؛ إثبات الرقم يعني التحكم في استلام الرسالة وليس التحقق من هوية الشخص.

**وضع عرض الـMVP معتمد بطلب المستخدم:** القيمة الافتراضية المحلية `AUTH_OTP_MODE=demo` تختار `DemoOtpSender`، ورمز التسجيل ثابت **`123456`** دون إرسال SMS. يرجع طلب الرمز `deliveryMode: "demo"`. هذه محاكاة للتحقق ولا تثبت ملكية الرقم؛ `phoneVerified` وتاريخ التحقق في حسابات العرض يعنيان اجتياز الخطوة التجريبية فقط. لا يُطبع الرمز أو السر في logs.

ما زال ربط SMS الحقيقي غير منفذ. اختيار `AUTH_OTP_MODE=disabled` يعيد سلوك `503 OTP_DELIVERY_UNAVAILABLE`. استبدال العرض مستقبلًا يتم بإضافة adapter في `src/integrations/sms/otp-sender.ts` وربطه في `createOtpSender`؛ لا يلزم تغيير رحلة التسجيل أو الجلسات. تُستخدم حسابات العرض في قاعدة عرض منفصلة عن حسابات التشغيل الحقيقي.

## الرحلة وعقد API

كل المسارات تحت `/api/v1`، والتفاصيل في `openapi.yaml`.

| المسار | الطلب/الوظيفة |
| --- | --- |
| `POST /auth/register/otp` | `{phone}`؛ يبدأ التحقق ويعيد `challengeId`, `expiresAt`, `retryAfterSeconds`, `deliveryMode`؛ في العرض استخدمي `123456` |
| `POST /auth/register` | `{phone, challengeId, otp, name, password, role}`؛ يستهلك OTP وينشئ الحساب والجلسة في معاملة واحدة |
| `POST /auth/login` | `{phone, password}`؛ الدخول للحساب الموثق والنشط |
| `POST /auth/refresh` | `{refreshToken}`؛ يستبدل رمزي access وrefresh |
| `POST /auth/logout` | `{refreshToken}`؛ يبطل الجلسة، ويعيد 204 بصورة idempotent |
| `GET /users/me` | Bearer access token؛ حساب الجلسة الحالية فقط |
| `GET /experts/me` | Bearer access token لخبيرة؛ ملفها وحالة اعتمادها دون مرجع وثيقة الهوية |
| `POST /auth/password/otp` | `{phone}`؛ تحقق OTP للاستعادة بحدود مستقلة عن التسجيل، دون كشف وجود الحساب |
| `POST /auth/password/reset` | `{phone, challengeId, otp, newPassword}`؛ يستهلك التحدي ويدوّر الهاش ويبطل كل الجلسات، ويعيد 204 دون إصدار جلسة |
| `POST /auth/password/change` | `{currentPassword, newPassword}` للجلسة الحالية؛ يتحقق من الحالية ويبطل كل الجلسات بما فيها الحالية (يلزم دخول جديد)، ويعيد 204 |
| `POST /auth/phone/otp` | `{phone}`؛ تحقق OTP للرقم الجديد بحدود الاستعادة |
| `POST /auth/phone/change` | `{phone, challengeId, otp}` للجلسة الحالية؛ ينقل الرقم بعد تحققه ويثبت تاريخ التحقق، والجلسات تبقى صالحة |
| `PATCH /users/me` | `{name?, cityId?}`؛ الحقول المسموحة فقط، والمدينة ضمن النطاق المفعّل |
| `POST /users/me/deactivate` | يعطل الحساب الحالي ويبطل جلساته (204)؛ التاريخ المالي والحجوزات محفوظة |
| `POST /admin/users/:id/deactivate` و`/reactivate` | للمدير على حسابات customer/expert فقط؛ ليس للمديرين ولا للنفس، مع تدقيق إداري وإبطال الجلسات عند التعطيل |
| `GET /admin/audit-logs` | قراءة سجل التدقيق بفلاتر `action` و`resourceType` و`actorId` ونطاق زمني وpagination، دون أسرار |

- التسجيل وOTP يقبلان المحمول المصري `01[0125]xxxxxxxx` أو `+201[0125]xxxxxxxx` ويخزنان الصيغة الدولية، بعد اعتماد القاهرة. الدخول فقط يدعم كذلك أرقام الحسابات السعودية السابقة؛ لا تسجيل سعودي جديد.
- التسجيل يقبل `customer` أو `expert` فقط. اسم من 2 إلى 100 حرف، وكلمة مرور من 12 إلى 128 حرفًا دون قص أو تحويل لحالتها. الحقول الإضافية تُرفض بـ422.
- تسجيل الخبيرة ينشئ ملفًا `pending` واستقبال الحجوزات معطلًا. يمكنها الدخول لمعرفة حالة ملفها؛ لا يعني الدخول اعتمادها للعمل.
- طلب OTP لا يكشف هل الهاتف مسجل سابقًا. يظهر `PHONE_ALREADY_REGISTERED` فقط بعد تقديم OTP صحيح؛ لا يُستبدل حساب قائم أو دوره أو كلمة مروره.
- مسار دخول الهاتف يرفض المدير كغيره بخطأ `INVALID_CREDENTIALS` عام. أصبح للمدير مسار منفصل `/admin/auth/login` مع audience مستقل؛ تفاصيل الدخول والتجديد والخروج وعزل الجلسات في `catalog.md`. واجهة Dashboard المرئية متبقية.
- لا يمكن اختيار صاحب `/users/me` أو `/experts/me` باستخدام معرف من التطبيق؛ المصدر هو الجلسة. لا يوجد endpoint لتعديل الدور أو اعتماد النفس.

## OTP والإرسال

- في وضع العرض الرمز `123456`، وفي مسار المزود دون مولد خاص يكون عشوائيًا من 6 أرقام باستخدام `crypto.randomInt`. في الحالتين صالح افتراضيًا 5 دقائق وحده 5 محاولات خاطئة.
- يخزن HMAC للرمز مع challenge ID والهاتف باستخدام `AUTH_SECRET`؛ لا يُخزن الرمز النصي.
- إعادة الطلب بعد cooldown تنشئ challenge جديدًا وتبطل السابق، مع تسلسل على الهاتف بقفل PostgreSQL داخل معاملة.
- الحفظ الأولي يتم قبل استدعاء المزود؛ الإرسال خارج معاملة البيانات. لا يمكن استخدام challenge قبل تسجيل نجاح طلب الإرسال. `delivered_at` يعني قبول sender للطلب، وفي وضع العرض هو قبول المحاكاة فقط.
- عند فشل الإرسال يُبطل challenge ويظهر 503. المحاولات الخاطئة تُحفظ حتى عند رد 400، ولا تتراجع بفعل rollback غير مقصود.
- التحقق واستهلاك الرمز وإنشاء الحساب وملف الخبيرة والجلسة عمليات ذرية. الطلبان المتزامنان باستخدام الرمز نفسه لا ينشئان حسابين.
- واجهة المزود في `src/integrations/sms/otp-sender.ts`. تنفيذ adapter الفعلي يحتاج مزودًا وحسابًا ووسيلة اختبار معتمدة. يجب على adapter ضبط timeout وعدم تسجيل الرمز أو أسرار المزود.

## كلمات المرور والجلسات

- كلمات المرور باستخدام scrypt بملح عشوائي مستقل، `N=32768, r=8, p=3` ومفتاح 64 بايت. لا توجد كلمات مرور نصية في القاعدة أو السجلات. الحساب غير الموجود يمر بتحقق scrypt وهمي لتقليل اختلاف وقت الاستجابة.
- **اختيار تنفيذي موثق:** رموز عشوائية opaque بطول عشوائي 256 bit، وليست JWT. JWT كان اقتراحًا في الخطة؛ اخترنا التحقق من الجلسة في PostgreSQL لدعم الإبطال المباشر والتحقق من نشاط الحساب بكل طلب، دون إضافة dependency للتوقيع.
- access token افتراضيًا 15 دقيقة، والجلسة ذات عمر مطلق 30 يومًا. التجديد لا يمدد العمر المطلق.
- يخزن SHA-256 للرموز فقط. القيم الأصلية تُعاد مرة في الاستجابة، مع `Cache-Control: no-store`.
- التدوير يبطل access السابق ويستهلك refresh السابق داخل معاملة مقفلة على الجلسة. تبقى بصمات refresh المستهلكة لكشف إعادة الاستخدام عبر العمليات وإعادة تشغيل الخادم.
- إعادة استخدام refresh مستهلك تبطل الجلسة كلها. إذا تزامن طلبا refresh، ينجح واحد والثاني يبطل الجلسة، بما فيها رموز الأول. على التطبيق تسلسل التجديد بطلب واحد وعدم إعادة إرسال refresh قديم تلقائيًا بعد timeout؛ عند فقدان النتيجة قد يلزم الدخول مجددًا.
- الخروج يبطل الجلسة المقصودة فقط، حتى لو انتهى access. تعطيل الحساب يمنع استخدام access والتجديد والدخول.
- العقد خاص بتطبيقات الهاتف: `Authorization: Bearer <accessToken>`، وrefresh في JSON. لا cookies ولا مصادقة ضمنية، وبالتالي لا يعتمد هذا العقد على حماية CSRF الخاصة بالـcookies. تخزين الرموز الآمن في Flutter وربط الشاشات لم يُنفذا.

## الحدود الافتراضية للمحاولات

حدود fixed-window مخزنة في PostgreSQL، وتعمل عبر عدة عمليات API. هوية الهاتف/IP في جدول العدادات مخزنة كـHMAC. المحاولات الفاشلة تُحتسب أيضًا.

| العملية | الحد |
| --- | --- |
| إرسال OTP لكل هاتف | مرة في 60 ثانية، و5 مرات في ساعة |
| إرسال OTP لكل IP | 20 في 10 دقائق |
| إنهاء التسجيل لكل IP | 20 في 10 دقائق |
| الدخول لكل هاتف | 10 في 15 دقيقة |
| الدخول لكل IP | 30 في 15 دقيقة |
| refresh أو logout لكل IP | 60 لكل عملية في دقيقة |
| استعادة/هاتف لكل IP | 20 في 10 دقائق |
| عمليات الحساب الموثقة لكل IP | 60 في دقيقة |

الرفض `429 RATE_LIMITED` مع `Retry-After`. `trust proxy` غير مفعل؛ X-Forwarded-For من العميل لا يغير عنوانه المعتمد. عند النشر خلف proxy يجب تحديد الوسطاء الموثوقين بدقة قبل تفعيل هذا الإعداد؛ وإلا ستُحسب طلبات المستخدمين على عنوان الوسيط نفسه.

## التخزين وmigrations

أُضيفت `0003_phone_password_auth.sql` دون تعديل migrations السابقة:

- `users.phone_verified_at`: اختياري للصفوف السابقة؛ لا تعتبر موثقة تلقائيًا. الدخول يتطلب تاريخ تحقق وpassword hash صالحًا.
- `auth_otp_challenges`: التحقق المؤقت والمحاولات واستهلاك الرمز.
- `auth_sessions`: عمر الجلسة وبصمة access والإبطال.
- `auth_refresh_tokens`: سلسلة رموز التجديد وبصماتها وتاريخ استهلاكها.
- `auth_rate_limits`: العدادات الدائمة.

جدول التدقيق الإداري أُضيف لاحقًا، ثم جداول `payment_provider_events` و`notification_outbox` و`idempotency_keys`، فأصبح المجموع الحالي **17 جدول أعمال + 8 جداول تقنية = 25**. تُنظف السجلات المنتهية دوريًا حسب سياسة الاحتفاظ في `docs/operations.md`، مع إبقاء سجل رموز التجديد طوال عمر الجلسة لضمان كشف إعادة الاستخدام.

## إعداد التشغيل

ملف `.env` المحلي و`.env.example` مجهزان للعرض بهذه القيم العامة التجريبية:

```dotenv
AUTH_OTP_MODE=demo
AUTH_SECRET=lamsa-demo-only-auth-secret-not-for-real-users
```

في وضع `demo` يُستخدم السر التجريبي نفسه إذا كان `AUTH_SECRET` غائبًا أو فارغًا، ويُحافظ على أي قيمة مخصصة غير فارغة. هذا fixture معلن وليس سرًا خاصًا. وضع العرض هو الافتراضي خارج `NODE_ENV=production`؛ في production يلزم اختياره صراحة إن كانت البيئة للعرض، وإلا يكون الوضع `disabled` ويتطلب `AUTH_SECRET` خاصًا. مثال توليد سر خاص عند الانتقال إلى ربط فعلي:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

ضع الناتج في `.env` محليًا ولا تُضفه إلى Git. المتغيرات الاختيارية: `AUTH_ACCESS_TTL_SECONDS=900`, `AUTH_SESSION_TTL_SECONDS=2592000`, `AUTH_OTP_TTL_SECONDS=300`. مدد OTP والجلسات لا تحدد مهلة قبول الحجز أو دفعه. تبقى قيود المحاولات وضرورة طلب challenge أولًا واستهلاكه مرة واحدة سارية مع الرمز الثابت.

يمكن التسجيل والدخول في العرض دون مزود SMS. التكامل الحقيقي يحتاج adapter مزود لاحقًا، وليس مجرد تغيير اسم الإعداد. أوامر migrations لا تحتاج سر Auth. تغيير وضع التشغيل أو سر Auth لا يحول حسابات العرض القديمة تلقائيًا إلى أرقام موثقة فعليًا.

## المتبقي

ربط SMS حقيقي وتجربة تسجيل عبره، واجهة Dashboard، واجهات Flutter. دخول المدير عبر API منفذ ومعزول عن جلسات الهاتف. لا تُعد المرحلة R1 مكتملة بهذه المهمة وحدها.

## حدود الاستعادة في وضع العرض

رمز العرض الثابت `123456` معلن، فأي شخص يعرف رقم هاتف يستطيع تدوير كلمة مروره في بيئة العرض. هذا مقبول للتجربة المحلية فقط؛ في التشغيل الحقيقي يتطلب الأمر مزود SMS فعليًا. طلب الاستعادة لا يكشف وجود الحساب، لكن خطوة التأكيد (بعد OTP صحيح) تعيد 404 لرقم بلا حساب.
