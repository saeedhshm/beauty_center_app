## القرار المعتمد: حجز الفترة يبدأ عند القبول

وافق المستخدم على السماح بطلبات `pending` متداخلة، وحجز الفترة عند قبول الخبيرة (`accepted`) بانتظار الدفع. قيد `bookings_expert_period_exclusion` يطبق:

```sql
EXCLUDE USING gist (
  expert_id WITH =,
  tstzrange(starts_at, ends_at, '[)') WITH &&
)
WHERE (status IN ('accepted', 'confirmed', 'completed'))
```

- يستمر المنع بعد التأكيد، ويحتفظ `completed` بعدم التداخل التاريخي.
- `pending`, `rejected`, `cancelled`, `expired` لا تدخل القيد.
- الفترات نصف مفتوحة `[start, end)`؛ موعدين متتاليين لا يتداخلان. إضافة وقت انتقال مستقبلًا تتطلب سياسة صريحة.
- رفض PostgreSQL للقيد يحمل SQLSTATE `23P01`. عند تنفيذ API يجب تحويله إلى `409` مفهومة؛ هذا التحويل ومسار القبول لم يُنفذا بعد.
- `expires_at` حقل اختياري دون default داخل الجدول. السياسة المعتمدة والمخزنة حاليًا 10 دقائق للقبول و10 للدفع، قابلة للتعديل إداريًا. محرك الحجز والـWorker متبقيان؛ مرور الوقت وحده لا يحرر الفترة.
- لا تُرفض الطلبات المتداخلة الأخرى تلقائيًا بمجرد قبول أحدها؛ مصيرها وانتقالاتها جزء من سياسة محرك الحجز لاحقًا.

## اختيارات التمثيل التنفيذية

- UUID للكيانات التشغيلية وsmallint identity للمدن والخدمات. أُضيفت القاهرة مفعّلة بقرار المستخدم، وبيانات عرض محلية منفصلة عبر seed صريح قابل للتكرار.
- `users.role` مطلوب ومقيّد بالأدوار الثلاثة؛ ليس له default يسمح بإنشاء مدير تلقائيًا. اعتُمد الهاتف وكلمة المرور مع OTP التسجيل. `password_hash` و`phone_verified_at` اختياريان للصفوف السابقة، لكن مسارات الدخول ترفض الحساب غير الموثق أو الذي لا يملك hash صالحًا؛ التسجيل الجديد يملأهما.
- حالة اعتماد الخبيرة منفصلة عن `users.is_active` و`expert_profiles.is_accepting_bookings`؛ لا تُفعّل الخبيرة لاستقبال الطلبات افتراضيًا.
- الجداول القابلة للتعديل تحتوي `created_at` و`updated_at` افتراضيًا عند الإنشاء. تحديث `updated_at` مسؤولية استعلامات التطبيق؛ لا يوجد trigger تلقائي حاليًا. سجل الحالات والإشعارات لهما `created_at`، والإشعارات `read_at`.
- `changed_by` و`cancelled_by` معرفا مستخدم؛ `changed_by = NULL` يمثل حدث النظام. لا تُفرض سياسة إلغاء تلقائي غير معتمدة.
- العنوان والفترة والمبالغ داخل الحجز لقطات مستقلة. لا يوجد FK من الحجز إلى عنوان محفوظ، وتغيير المصدر لا يعيد حساب اللقطة. منع تعديل اللقطات مباشرة عبر API مسؤولية خدمة الحجز القادمة.
- الإحداثيات اختيارية كزوج، بدقة 6 منازل وبحدود latitude/longitude. يوجد فهرس جزئي يسمح بعنوان افتراضي واحد كحد أقصى لكل عميلة؛ لا يفرض وجود عنوان افتراضي دائمًا.
- الأموال `numeric(10,2)`، والنسب `numeric(7,4)` بوحدة النسبة المئوية: `20.0000` تعني 20% وليس 0.20. القيم المالية غير سالبة ومحدودة بما يمنع PostgreSQL numeric NaN، والنسب بين 0 و100.
- لا default لمبالغ لقطة الحجز أو نسبها داخل الجدول، ولا CHECK لمعادلة مالية غير معتمدة. العمولة الافتراضية المعتمدة 20% محفوظة في settings وقابلة للتعديل؛ حسابها وحفظ اللقطة مسؤولية محرك الحجز القادم. التقريب والضريبة والرسوم لم تُحسم.
- ترقيم الأسبوع ISO: الاثنين=1 والأحد=7. وقت الجدول محلي وفق Africa/Cairo؛ الاستثناء له تاريخ محلي. غياب وقتَي الاستثناء معًا يمثل يومًا كاملًا. العمل نهارًا فقط بقرار المستخدم، لكن حدود النهار وأولوية الاستثناءات ومحرك المواعيد لم تُنفذ، فلا يُستنتج توفر صالح من التخزين وحده.
- `identity_document_key` مرجع تخزين لا رابط عام؛ لم يُنفذ مزود التخزين أو الوصول بعد.
- جميع العلاقات الحالية تستخدم `ON DELETE RESTRICT`. لا cascade يمحو التاريخ. حذف عنوان محفوظ غير مرتبط بالحجز يظل ممكنًا، وتعطيل الحساب هو المسار المقصود عند وجود تاريخ.
- FK مركب يضمن أن الحجز مرتبط بخدمة تقدمها الخبيرة. FK آخر يمنع ربط الحجز بتحويل لخبيرة مختلفة.
- مرجع العملية فريد ضمن مزود الدفع `(provider, provider_ref)`؛ المرجع يمكن أن يكون NULL قبل استلامه. هذا ليس بديلًا عن تخزين أحداث Webhook أو منع تكرار التحصيل؛ لم تُنفذ هذه الآليات بعد.
- `payouts` يوفر مرجع تحويل ووقته دون اختراع حالات سير عمل أو أهلية صرف. وجود سجل لا يثبت تنفيذ تحويل بنكي.

## الضمانات التي لم تُنفذ بعد

CHECK الحالات لا يفرض State Machine. كذلك FK إلى مستخدم لا يثبت دوره أو صلاحياته. خدمة الحجز يجب أن تتحقق من الاعتماد والنشاط والملكية والتوفر والحالة الحالية، وتكتب الانتقال وسجله في المعاملة نفسها.

قيود reviews تمنع التكرار والتقييم الذاتي والدرجات خارج 1–5، لكن التحقق من اكتمال الحجز ومن طرفيه، وتحديث المتوسط، ما زال مسؤولية خدمات لاحقة. أهلية الصرف ومنع إعادة صرف حجز، والتأكيد بعد دفع موثوق، ليست ميزات منفذة بمجرد وجود الجداول.

## الاختبارات المعزولة

`tests/helpers/database-setup.ts` يتصل فقط بخادم Compose الاختباري على `127.0.0.1:55433`. ينشئ قاعدة فريدة باسم `lamsa_it_<uuid>` لكل تشغيل، يطبق migrations عليها، ثم يحذف **القاعدة التي أنشأها هذا التشغيل فقط** في teardown. لا يقرأ `DATABASE_URL` ولا يعيد ضبط قاعدة مستخدم.

اختبارات القيود والتزامن تستخدم اتصالات PostgreSQL حقيقية. اختبار التنافس يبقي معاملة القبول الأولى مفتوحة، ويتحقق من انتظار الثانية لقفل PostgreSQL، ثم يثبت نجاح الأولى ورفض الثانية دون أثر قبول ثانٍ. هذه اختبارات مستوى البيانات، وليست رحلة حجز عبر API.
