# الموثوقية — مفاتيح عدم التكرار والتنظيف الدوري

## مفتاح `Idempotency-Key` لإنشاء الحجز

إعادة إرسال `POST /api/v1/bookings` بعد timeout آمنة عند إرسال ترويسة
`Idempotency-Key` بقيمة UUID. المفتاح مربوط بالعميلة (`user_id, scope, key`
فريد)، والنطاق الحالي `booking.create`:

- أول طلب يثبت المفتاح `in_progress` ثم ينفذ الإنشاء، ويختم الصف `completed`
  مع رمز الحالة (201) ولقطة الاستجابة في المعاملة نفسها.
- تكرار نفس المفتاح يعيد الاستجابة المخزنة بنفس الرمز دون إنشاء حجز ثانٍ.
- طلب متزامن أثناء التنفيذ يرد 409 `IDEMPOTENCY_IN_PROGRESS`.
- فشل الإنشاء يحرر المفتاح ليعيد العميل المحاولة نظيفًا بنفس القيمة.
- الصفوف تعيش 24 ساعة وتُقرأ المنتهية كأنها غائبة؛ مهمة التنظيف تحذفها بعد
  انتهائها. لا تُستخدم المفاتيح لأي عملية مالية مباشرة خارج إنشاء الحجز.

## مهمة التنظيف الدوري

`cleanupExpiredRecords` في `src/jobs/cleanup.ts` تعمل ضمن نبضة الـWorker
(`npm run worker`) بعد الانتهاء والتسليم، وتعيد أعدادًا فقط للسجلات:

| الجدول | القاعدة |
| --- | --- |
| `auth_otp_challenges` | `expires_at` أقدم من 24 ساعة (هاشات فقط) |
| `auth_sessions` | `expires_at` أقدم من 7 أيام (بعدها لا حاجة لكشف إعادة الاستخدام) |
| `auth_refresh_tokens` | رموز جلسات تجاوزت المهلة نفسها أولًا (قيد `restrict`) |
| `auth_rate_limits` | `resets_at` منتهية |
| `idempotency_keys` | `expires_at` منتهية |
| `notification_outbox` | صفوف `sent`/`failed` أقدم من 30 يومًا |

لا تُمس أبدًا: `users` والحجوزات والمدفوعات والمستحقات والتقييمات والإشعارات
نفسها وأحداث المزود وسجل التدقيق — التاريخ المالي والحسابي محفوظ. الإشعارات
المقروءة للمستخدمين لا تُحذف لعدم وجود سياسة احتفاظ معتمدة لها بعد.

## المتبقي

سياسة احتفاظ معتمدة لإشعارات المستخدمين، وتنبيه تشغيلي عند تراكم صفوف `failed`
في الـoutbox.

## التشغيل (D6)

- **العمليتان**: `npm run build` ثم API (`npm run start`) والـWorker (`npm run worker:start`)
  كعمليتين منفصلتين؛ الـWorker وحده ينفذ `tickBookingSla` و`deliverOutboxBatch`
  و`cleanupExpiredRecords` ويسجل نبضته في `worker_heartbeats` (تظهر في
  `GET /api/v1/admin/overview` وصفحة التشغيل).
- **قاعدة البيانات**: migrations عبر `npm run db:migrate` فقط، دون إسقاط أو reset
  لقاعدة قائمة؛ النسخ الاحتياطي قبل أي ترقية (لا يوجد staging بعد — انظر المتبقي).
- **المتغيرات**: كلها في `.env.example` بلا أسرار حقيقية؛ `AUTH_SECRET` و`DATABASE_URL`
  وبيانات المزودين الحقيقيين عند اعتمادهم تُحقن من بيئة الاستضافة لا من Git.
- **الواجهة**: Dashboard مبني بـ`npm run build` يُقدَّم خلف reverse proxy يمرر `/api`
  إلى Backend على نفس المصدر؛ لا CORS عام في Backend (التصميم same-origin، و helmet
  مفعّل). للمنافذ البديلة في التطوير فقط `DASHBOARD_API_TARGET`.
- **السجلات والمراقبة**: كل استجابة تحمل `requestId`؛ الأخطاء تُسجل بلا كلمات مرور
  أو توكنات أو بيانات دفع (`LOG_LEVEL` يتحكم في الإسهاب). لا مفتاح تتبع أخطاء
  للواجهة بعد — القرار مؤجل مع اختيار المزود (يُمنع إرسال أي حقل شخصي أو مالي).
- **ليست جاهزة للإنتاج بعد**: لا staging، لا نسخ احتياطي مجدول، لا مزودو
  SMS/Push/Payment حقيقيون (الوضع الحالي Demo معلن في الواجهة)، ولا تنبيه
  `failed`-outbox. انظر `PROJECT_STATUS.md` لما تحقق فعلًا.
